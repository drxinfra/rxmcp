# rxmcp: архитектура

MCP-сервер для Directum RX. Даёт ИИ-ассистенту (Claude Desktop, Claude Code, Cursor и любому другому хосту с поддержкой MCP) доступ к задачам, заданиям и документам пользователя RX через штатный сервис интеграции (OData). Ничего, кроме публичного интеграционного API, не использует: ни базы, ни конфигов, ни внутренних сервисов RX. Что куда уходит и что лежит на диске, с точки зрения рисков: [security.md](security.md).

## Роли и транспорт

```
пользователь ── хост (Claude Desktop / Cursor / Claude Code)
                  │ JSON-RPC 2.0, stdio
                  ▼
               rxmcp (этот бинарник, на машине пользователя)
                  │ HTTPS, OData 4, учётка пользователя
                  ▼
               Directum RX, сервис интеграции  /Integration/odata
```

- Транспорт по умолчанию stdio: хост сам запускает `rxmcp`, общается через stdin/stdout. Все логи только в stderr.
- Второй режим `rxmcp serve --http`: Streamable HTTP для установки рядом с RX. Два варианта входа: общий секрет в заголовке и одна учётка RX на всех (`RXMCP_HTTP_AUTH=secret`) или токен сотрудника от провайдера OIDC, с которым сервер ходит в RX под его учёткой (`RXMCP_HTTP_AUTH=oidc`, с 0.12). Подробно в [security.md](security.md).
- В stdio и в HTTP с общим секретом один процесс = одна учётка RX. Права ровно те, что у этого пользователя в RX; сервер их не расширяет и не обходит. Несколько систем подключаются несколькими серверами с разными `RXMCP_HOME`: `setup` регистрирует второй под именем `rx-<хост>` с `RXMCP_HOME` в окружении, хост виден модели в названии и описании сервера.

## Аутентификация в RX

Сервис интеграции RX на 401 объявляет сразу несколько схем: `Basic`, `Bearer`, `Negotiate` и редирект на форму входа (cookie). Какие из них реально работают, зависит от того, как настроен сервер: только пароль, Windows-домен, Keycloak или другой OIDC-провайдер. rxmcp умеет так:

| `RXMCP_AUTH` | Что шлём | Когда подходит |
|---|---|---|
| `basic` (по умолчанию) | `Authorization: Basic` | у пользователя есть логин типа «пароль»; небольшие внедрения без домена |
| `header` | заголовки `Username` / `Password` | старые версии, где Basic не включён |
| `oidc` | `Authorization: Bearer` с токеном, который rxmcp сам получил у провайдера | RX за Keycloak или другим OIDC; `rxmcp login` открывает браузер, пароль вводится там, дальше токен обновляется сам |
| `bearer` | `Authorization: Bearer <RXMCP_TOKEN>` | токен получен снаружи |
| `cookie` | заголовок `Cookie` из браузера после входа в RX | быстрый обходной путь, когда OIDC-клиент ещё не заведён; живёт, пока живёт сессия |
| `cookie` + `login --sso` | копия сессии провайдера (для Keycloak `KEYCLOAK_IDENTITY` и соседние куки) | RX сам выполняет OIDC (form_post на `/Client/b1`), rxmcp на 401 проходит ту же цепочку: `/Client/login` → провайдер → `/Client/b1` → `login.auto-logon-with-two-factor` и получает новую `sungero_client`; живёт, пока жива сессия провайдера (`internal/weblogin`) |
| `negotiate` | Kerberos/NTLM от доменной учётки | в планах: на Windows через SSPI без ввода пароля, на Linux по билету Kerberos |

Для `oidc` администратору провайдера нужно завести публичный клиент (например `rxmcp`). Для входа по коду авторизации (`RXMCP_OIDC_FLOW=code`, по умолчанию) нужен redirect URI `http://127.0.0.1:*/callback`; для device flow (`RXMCP_OIDC_FLOW=device`) redirect URI не нужен вовсе, достаточно включить у клиента OAuth Device Authorization Grant. Секрет клиента не обязателен. Переиспользовать client_id веб-клиента RX можно, только если он разрешает нужный flow; это решает администратор. Сервис интеграции должен принимать токены этого провайдера (тот же issuer, что у веб-клиента RX); это проверяется командой `rxmcp check` после `rxmcp login`.

Во всех режимах, кроме `basic` и `header`, RX не сообщает, кто мы, поэтому нужен `RXMCP_LOGIN` (логин, по которому ищем пользователя в справочнике) или `RXMCP_USER_ID`.

## Что сервер отдаёт хосту

### Инструменты чтения (всегда включены)

| Инструмент | Что делает | Запрос к RX |
|---|---|---|
| `rx_whoami` | кто я в RX: Id, имя, подразделение, должность | `IUsers` по логину, `IEmployees(Id)` |
| `rx_my_assignments` | мои задания: в работе (по умолчанию), просроченные, непрочитанные, выполненные | `IAssignments?$filter=Performer/Id eq …` |
| `rx_get_assignment` | задание целиком: тема, автор, срок, переписка, вложения | `IAssignments(Id)?$expand=Texts,AttachmentDetails,…` |
| `rx_get_task` | задача целиком: статус, автор, переписка, вложения, задания по ней | `ITasks(Id)`, `IAssignments?$filter=Task/Id eq …` |
| `rx_list_tasks` | задачи, где я автор или наблюдатель, по статусу и теме | `ITasks?$filter=Author/Id eq …` |
| `rx_find_documents` | поиск документов по названию, виду, дате, автору, номеру | `IOfficialDocuments` или `IElectronicDocuments` |
| `rx_get_document` | карточка документа: вид, состояние, регистрация, версии | `IElectronicDocuments(Id)?$expand=Versions,…` |
| `rx_get_document_text` | текст версии (docx, xlsx, pptx, pdf, txt, md, csv, json, xml, html, rtf); скан и картинка возвращаются изображениями страниц | `…/Versions(Id)/Body` |
| `rx_whats_new` | что нового с прошлого вызова: пришедшие задания и уведомления, срок до конца дня, завершённые мои задачи | `IAssignments`, `INotices` с `Created ge`, `ITasks` с `Modified ge` |
| `rx_find_employees` | найти сотрудника по фамилии, чтобы получить Id для поручений | `IEmployees?$filter=contains(Name,…)` |

### Коробочные модули (чтение)

| Инструмент | Что делает | Запрос к RX |
|---|---|---|
| `rx_kb_areas` | области базы знаний со стартовыми статьями | `IAreaOfExpertises` |
| `rx_kb_search` | статьи по названию, области, тегу, автору | `IMemoArticles` с `Areas/any`, `Tags/any` |
| `rx_kb_article` | статья с текстом (markdown из тела версии) | `IMemoArticles(Id)`, `…/Versions(Id)/Body/$value` |
| `rx_boards`, `rx_board` | agile-доски; доска с колонками по порядку и карточками | `IBoards`, `IColumns?$expand=Tickets($expand=Ticket)` |
| `rx_tickets`, `rx_ticket` | поиск карточек по названию или коду; карточка целиком | `ITickets` |
| `rx_ticket_history` | история карточки, как вкладка «История»: события от старых к новым | `GET History/GetHistory(entityGuid, entityId)` с типом карточки: JSON строкой, записи «поле получило значение» без прежнего; колонка числом в `ColunmId` (опечатка RX), имена из `IColumns` доски, удалённые колонки только номером |
| `rx_projects`, `rx_project` | проекты и инициативы; карточка с командой, гейтами и планами | `IProjectCores`, `IProjectPlanRXs?$filter=Project/Id` |
| `rx_project_plans`, `rx_project_plan` | планы проектов; дерево работ с ответственными и просрочками | `IProjectPlanRXs`, модель плана из тела версии (JSON) |

Всё это стандартные модули «Знания», «Agile-доски» и «Проекты». Прикладные надстройки поверх них (дополнительные поля, свои сущности) сервер не читает, поэтому работает на любом внедрении, где эти модули есть.

### Справка системы (чтение)

| Инструмент | Что делает |
|---|---|
| `rx_help_search` | поиск по справке стенда: BM25 по основам слов, заголовок и раздел весят больше текста |
| `rx_help_topic` | текст статьи; внутренние ссылки остаются как `[текст](файл.htm)`, по ним можно идти дальше |
| `rx_help_toc` | оглавление: верхний уровень или содержимое раздела |

Справка скачивается со стенда пользователя (`<адрес RX>/Client/WebHelp/ru-RU`, перенаправления учитываются): оглавление `hmcontent.htm` и статьи, тело между метками `ZOOMRESTART` и `ZOOMSTOP`. В поставке её нет, потому что содержимое принадлежит вендору. Индекс хранится в каталоге настроек, один файл на стенд. Если индекса нет, первый вызов запускает скачивание в фоне и сообщает об этом; остальные инструменты в это время работают.

Эмбеддингов нет намеренно: они требуют модели на сотни мегабайт и отдельной среды выполнения, а сервер это один файл. Семантику закрывает сам помощник, переформулируя запрос.

### Любая сущность (чтение)

| Инструмент | Что делает | Запрос к RX |
|---|---|---|
| `rx_find_entity` | наборы сущностей по названию; русские слова переводятся в корни английских имён | `$metadata`, один раз за сеанс |
| `rx_describe_entity` | поля и ссылки набора с учётом наследования | из того же `$metadata` |
| `rx_query` | одна запись по Id или список по `filter`, `select`, `expand`, `orderby` | `GET {набор}` или `GET {набор}(Id)` |

Это запасной выход для данных, под которые нет готового инструмента. Имя набора проверяется на допустимые символы, список ограничен ста записями, ответ обрезается по общему лимиту текста. Запись сюда не входит: с флагом записи добавляется только `rx_call_action`, вызов действия модуля с подтверждением. Создавать, менять и удалять произвольные сущности сервер не умеет.

### Инструменты записи (только с `RXMCP_ALLOW_WRITE=1`)

Без флага эти инструменты не регистрируются вовсе: модель их не видит и не может вызвать.

| Инструмент | Что делает | Запрос к RX |
|---|---|---|
| `rx_complete_assignment` | выполнить задание с результатом | `POST Docflow/CompleteAssignment` |
| `rx_create_simple_task` | создать простую задачу исполнителям и стартовать | `POST Docflow/CreateSimpleTask`, затем `Docflow/StartTask` |
| `rx_abort_task` | прекратить задачу | `POST Shell/AbortTask` |
| `rx_send_for_acquaintance` | отправить документ на ознакомление | `POST RecordManagement/CreateAcquaintanceTask`, затем `Docflow/StartTask`: действие только сохраняет черновик |
| `rx_send_for_approval` | свободное согласование или по регламенту | `POST Docflow/CreateFreeApprovalTask` или `CreateApprovalTask` (маршрут по правилу RX, указанные люди сверх правила), затем `Docflow/StartTask` |
| `rx_create_article`, `rx_update_article` | статья базы знаний: создать в области, изменить название и текст | `POST IMemoArticles` с `Areas`, `MemoRX/CreateMemoVersion`; `MemoRX/UpdateArticleTitle`. Если текст не записался, пустая статья убирается `MemoRX/DeleteEmptyArticleById` |
| `rx_create_ticket`, `rx_update_ticket` | завести карточку; изменить, перенести, добавить вложения | `POST AgileBoards/SaveTicket`; вложение это запись «название и адрес» со `State: Added`. Файл сначала уходит в `AgileBoards/UploadPersistedBinaryData` (base64) и получает адрес `storage://<Id>&<тип>`, документ RX прикладывается гиперссылкой `Sungero?type=…&id=…` |
| `rx_comment_ticket` | добавить комментарий к карточке; читает комментарии `rx_ticket` | `POST TeamsCommonAPI/CreateComment` и `LoadComments`: кроме Id карточки и доски нужны идентификаторы их типов, они зашиты в `internal/rx/comments.go` и заменяются через `RXMCP_TICKET_TYPE_GUID`, `RXMCP_BOARD_TYPE_GUID` |
| `rx_edit_comment`, `rx_delete_comment` | исправить или удалить свой комментарий; автор сверяется с `rx_whoami` | `POST TeamsCommonAPI/UpdateComment` (`commentId`, `comment`) и `DeleteComment` (`commentId`, `appId`) |
| `rx_delete_tickets` | удалить карточки с доски; карточка остаётся в `ITickets` со статусом `Deleted` | `POST AgileBoards/RemoveTickets` по Id ссылок карточек на колонки (`IColumns?$expand=Tickets`), а не по Id карточек |
| `rx_create_column` | колонка на доске | `POST AgileBoards/CreateColumn` (в конец, «Новая колонка»), `UpdateColumnConfig` (имя, финальная, лимит), `MoveColumn` (место, с нуля) |

Результаты заданий для `rx_complete_assignment` взяты из метаданных модулей вендора (Docflow, DocflowApproval, RecordManagement версии 25.2), а не угаданы: у каждого типа задания свой набор, первый в списке подставляется по умолчанию, русские синонимы приводятся по смыслу («на доработку» это `ForRework` у свободного согласования и `ForRevision` у согласования по регламенту). Свободное согласование в 25.x порождает задания модуля DocflowApproval (`EntityApprovalAssignment`). Задания на подписание сервер не выполняет, и подписи вне задач (`Docflow/ApproveDocument`, `EndorseDocument`) сознательно не добавлены: если у пользователя один сертификат, это квалифицированная электронная подпись, её должен ставить человек.

Проверено вживую на тестовом стенде 25.2: статья создаётся, правится и читается; ознакомление и свободное согласование стартуют, задания `AcquaintanceAssignment` (`Acquainted`), `EntityApprovalAssignment` (`Approved`), `AcquaintanceFinishAssignment` и `AdvancedAssignment` (`Complete`) выполняются, задачи закрываются. Согласование по регламенту вживую не запускалось: правило разослало бы задания реальным участникам маршрута. Права: на внедрениях создание статей часто дано отдельным ролям, а задачи на ознакомление требуют роли «Пользователи с доступом к делопроизводству»; без прав RX отвечает понятной ошибкой, и сервер её передаёт.

Перед каждым действием записи сервер запрашивает у хоста подтверждение пользователя (elicitation). Если хост elicitation не поддерживает, действие всё равно выполняется: флаг записи уже явное согласие, а хосты и сами спрашивают перед вызовом инструментов без `readOnlyHint`. Хост, который заявил elicitation, но форму не показывает и отвечает отказом, сделает запись невозможной; для него `RXMCP_CONFIRM=0` выключает форму.

### Ресурсы

`rx://assignment/{id}`, `rx://task/{id}`, `rx://document/{id}`: те же карточки текстом, для подкладывания в контекст руками.

### Промпты

- `daily_review`: разбор моих заданий на сегодня, просрочки, порядок.
- `summarize_document`: краткое содержание документа по Id.

### PDF и сканы

Текстовый слой PDF извлекается копией библиотеки `ledongthuc/pdf` (BSD-3-Clause) в `internal/thirdparty/pdf`. Без правок она годилась только для PDF из Word, поэтому в копии:

- таблица ToUnicode главнее поля Encoding (иначе PDF из Chrome со шрифтами Type 3 давали мусор);
- положение текста считается по полной текстовой матрице и матрице страницы (`cm`, `q`/`Q`, `Td`, `TD`, `T*`), строки собираются по координатам;
- крупный сдвиг в `TJ` считается пробелом (LaTeX не пишет пробелы символами);
- принимаются PDF 2.0 и заголовок с пробелом.

На 37 реальных PDF (инструкции Directum, статьи, книга, выгрузки из Chrome и Aspose) доля слов, совпавших с `pdftotext` из poppler, от 0,80 до 1,0, у большинства выше 0,95. Колонки, стоящие рядом, разделяются табуляцией.

Если текста меньше 40 букв на страницу, PDF считается сканом. Если меньше 300, текст отдаётся вместе с картинками страниц. Картинки достаются прямо из байтов файла, а не через библиотеку: она не отдаёт поток без раскодирования. Поддержаны JPEG (DCTDecode), CCITT G3 и G4 (`golang.org/x/image/ccitt`), Flate и несжатые отсчёты в градациях серого и RGB с PNG-предикторами. Маски (`SMask`, `ImageMask`) и мелкие картинки (логотипы, подписи, меньше 300 точек по стороне) страницами не считаются. Каждая страница уменьшается до 1600 точек по длинной стороне и уходит модели как `ImageContent` в JPEG, по умолчанию 3 страницы за вызов, не больше 10. OCR внутри сервера нет: распознавание даёт модель, а встроенный движок весил бы сотни мегабайт. JBIG2 и JPEG 2000 не поддержаны, о них сервер говорит прямо.

### Что нового

`rx_whats_new` хранит отметку прошлого просмотра в `whatsnew-<хост>-<логин>.json` в каталоге настроек: только время, без данных RX. Первый вызов показывает последние сутки. `peek=true` смотрит, не сдвигая отметку. Подписки MCP на ресурсы для этого не подошли: большинство клиентов обновления до модели не доносит, а stdio-сервер работает, только пока открыт клиент.

## Принципы

1. **Мало инструментов, крупных.** Готовые инструменты покрывают рабочий день. Для остального есть три инструмента каталога: найти сущность, посмотреть поля, прочитать. Тысячу сущностей в отдельные инструменты не превращаем.
2. **Текст, а не JSON.** Ответы готовых инструментов форматируются компактным русским текстом: одна строка на задание, даты по-человечески, Id в скобках. Исключение одно: `rx_query` отдаёт записи как компактный JSON, потому что состав полей заранее неизвестен.
3. **Лимиты везде.** Списки по умолчанию 20, максимум 100. Текст документа по умолчанию 20 000 символов. Тело документа не грузим, пока не попросят явно.
4. **Чтение по умолчанию.** Запись только по флагу и с подтверждением. Удалять можно только карточки с доски (инструмент помечен `destructiveHint`); документы, задачи и прочие сущности сервер не удаляет.
5. **Содержимое RX не доверенное.** Тема задания или текст документа могут содержать инструкции для модели. Сервер помечает такие данные как содержимое, а не команды, и никогда не выполняет цепочку «прочитал и сразу отправил» без явного вызова инструмента записи.
6. **Данные пользователя не храним.** Нет кэша ответов RX, нет базы, нет телеметрии. Единственное соединение не к RX это проверка новой версии раз в сутки (`latest.txt` на зеркале, при недоступности GitHub), без данных пользователя; `RXMCP_UPDATE_CHECK=0` её выключает. На диске лежит только индекс справки вендора, скачанный со стенда. Остальное состояние это профиль, cookie, сессия провайдера (`login --sso`) и токены OIDC в `~/.config/rxmcp` с правами `0600`; в логи секреты не попадают. Секретов в конфиге ИИ-клиента нет, потому что обновление cookie не должно требовать правки JSON и перезапуска клиента.
7. **Совместимость.** Готовые инструменты используют только стандартные сущности и действия платформы Sungero (Workflow, Docflow, Content, CoreEntities, Company, Shell). Прикладные модули заказчика у всех разные, до них помощник добирается через каталог: читает их описание из `$metadata` самой системы.

## Модель ошибок

- 401 от RX: подсказка по режиму входа (проверить пароль, обновить cookie, `rxmcp login`). При `cookie` с сессией провайдера сервер сначала сам получает новую cookie и повторяет запрос, и только если это не вышло, отдаёт ошибку.
- 403: нет доступа к объекту или к сервису интеграции.
- 404 на чтении: «объект не найден или недоступен» (RX не различает). 404 на действии модуля (POST): RX так отвечает, когда не хватает обязательного параметра, об этом и говорится.
- Остальные ответы RX: код, метод, путь и текст ошибки RX, если он есть (например, недопустимый элемент перечисления).
- Сетевые ошибки: адрес и таймаут, без тела.
- Ошибки инструментов возвращаются как `isError` с текстом для модели, чтобы она могла объяснить пользователю и не повторять вызов вслепую.

## Проверка на живой системе

`rxmcp check` делает только GET-запросы: метаданные, кто я, счётчик заданий, один документ, одна версия. Печатает, что работает, а что нет, и подсказывает, что поправить. Годится для рабочей системы.

## Обновления

При старте сервера фоновая проверка узнаёт последнюю версию: `GET https://drxinfra.ru/dl/rxmcp/latest.txt`, при ошибке `HEAD github.com/drxinfra/rxmcp/releases/latest` и номер из редиректа. Ответ запоминается в `update-check.json` на сутки. Сборки не из релиза (`dev`, `v0.8.0-3-gabc`) не проверяются. Если версия новее, middleware сервера дописывает строку к первому успешному ответу инструмента за процесс; `rx_whoami` показывает версию сервера и новость всегда. Уведомления MCP для этого не годятся: большинство клиентов их пользователю не показывает.

`rxmcp update` скачивает архив сначала из релиза GitHub, потом с зеркала, и принимает его, только если сумма совпала с `SHA256SUMS` того же источника. Новый бинарник пишется рядом, старый отодвигается в `.old`, новый переименовывается на его место: запущенный в клиенте сервер замене не мешает. На Windows `.old` удаляется при следующем обновлении.

## Что проверено вживую

Сервис интеграции RX отвечает `204` без тела на пустую выборку, `404` на отсутствующий объект, `400` с текстом на неверный `$expand`. Действия модулей отвечают `404` с пустым телом, если не хватает обязательного параметра: у `CreateSimpleTask` обязателен `deadline`, у `CompleteAssignment` обязателен `result`. Результаты стандартных заданий: простое задание `Complete`, приёмка работ (ReviewAssignment) `Accepted` или `ForRework`; неверное значение даёт `400` с текстом «Элемент перечисления Result … недопустим». rxmcp подставляет стандартный результат по типу задания и понимает синонимы («принять», «на доработку»). Фильтры по навигационным свойствам (`Performer/Id eq …`, `Areas/any(…)`) и вложенный `$expand(…;$select)` работают. Вид документа (`DocumentKind`) есть только у официальных документов.

## Что не сделано

- Negotiate: SSPI на Windows, Kerberos на Linux.
- Сканы в JBIG2 и JPEG 2000 (компактный PDF у части МФУ): нужен свой декодер на Go.
- Отметка рабочего времени (модуль TimeTracker, есть не на всех стендах): табель за период (`TimeTracker/GetTimeSheet`), поиск работ, на которые списывать (`FindWorkItems`, `FindLeadObjects`), и списание часов (`SaveTimeSheet`). Проверять только на тестовой учётке.
- Полнотекстовый поиск по содержимому документов: в сервисе интеграции его нет, есть только у модуля вендора `IntegrationAIAgent` (`HandleMcpRequest`, нужна лицензия модуля).
- Пакет `.mcpb` для установки в Claude Desktop одним щелчком.

Сознательно не делаем: подписание документов (задания на подписание, `ApproveDocument`, `EndorseDocument`) и создание, изменение и удаление произвольных сущностей через каталог.
