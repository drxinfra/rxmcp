# rxmcp: архитектура

MCP-сервер для Directum RX. Даёт ИИ-ассистенту (Claude Desktop, Claude Code, Cursor и любому другому хосту с поддержкой MCP) доступ к задачам, заданиям и документам пользователя RX через штатный сервис интеграции (OData). Ничего, кроме публичного интеграционного API, не использует: ни базы, ни конфигов, ни внутренних сервисов RX.

## Роли и транспорт

```
пользователь ── хост (Claude Desktop / Cursor / Claude Code)
                  │ JSON-RPC 2.0, stdio
                  ▼
               rxmcp (этот бинарник, на машине пользователя)
                  │ HTTPS, OData 4, учётка пользователя
                  ▼
               Directum RX, сервис интеграции  /Integration/odata
```

- Транспорт по умолчанию stdio: хост сам запускает `rxmcp`, общается через stdin/stdout. Все логи только в stderr.
- Второй режим `rxmcp serve --http`: Streamable HTTP для установки рядом с RX. В этом режиме сервер работает от одной учётки RX и закрыт общим секретом в заголовке. Персональные учётки через HTTP появятся позже.
- Один процесс = одна учётка RX. Права ровно те, что у этого пользователя в RX; сервер их не расширяет и не обходит.

## Аутентификация в RX

Сервис интеграции RX принимает логин и пароль. rxmcp поддерживает три способа передать их:

| `RXMCP_AUTH` | Что шлём | Когда |
|---|---|---|
| `basic` (по умолчанию) | `Authorization: Basic` | обычная установка |
| `header` | заголовки `Username` / `Password` | старые версии, где Basic не включён |
| `bearer` | `Authorization: Bearer <RXMCP_TOKEN>` | токен получен снаружи (обратный прокси, Identity-сервис) |

Важно про типы входа. В RX у пользователя может быть вход по паролю, по Windows-учётке, через SAML или OIDC. Сервис интеграции проверяет только логин с паролем, это ограничение самого RX. Поэтому:

- у пользователя с Windows/SAML/OIDC-входом должен быть дополнительный логин типа «пароль» в RX, либо
- для интеграции заводится отдельная учётка с нужными правами.

Kerberos/NTLM напрямую из rxmcp в планах, делать будем по запросу.

Если сервер не может вычислить, кто мы (например, при `bearer`), пользователя RX задают явно через `RXMCP_USER_ID`.

## Что сервер отдаёт хосту

### Инструменты чтения (всегда включены)

| Инструмент | Что делает | Запрос к RX |
|---|---|---|
| `rx_whoami` | кто я в RX: Id, имя, подразделение, должность | `IUsers` по логину, `IEmployees(Id)` |
| `rx_my_assignments` | мои задания: в работе (по умолчанию), просроченные, непрочитанные, выполненные | `IAssignments?$filter=Performer/Id eq …` |
| `rx_get_assignment` | задание целиком: тема, автор, срок, переписка, вложения | `IAssignments(Id)?$expand=Texts,AttachmentDetails,…` |
| `rx_get_task` | задача целиком: статус, автор, переписка, вложения, задания по ней | `ITasks(Id)`, `IAssignments?$filter=Task/Id eq …` |
| `rx_list_tasks` | задачи, где я автор или наблюдатель, по статусу и теме | `ITasks?$filter=Author/Id eq …` |
| `rx_find_documents` | поиск документов по названию, виду, дате, автору, номеру | `IOfficialDocuments` или `IElectronicDocuments` |
| `rx_get_document` | карточка документа: вид, состояние, регистрация, версии | `IElectronicDocuments(Id)?$expand=Versions,…` |
| `rx_get_document_text` | текст версии (docx, xlsx, txt, md, csv, json, xml, html); pdf и сканы не читаем | `…/Versions(Id)/Body` |
| `rx_find_employees` | найти сотрудника по фамилии, чтобы получить Id для поручений | `IEmployees?$filter=contains(Name,…)` |

### Инструменты записи (только с `RXMCP_ALLOW_WRITE=1`)

Без флага эти инструменты не регистрируются вовсе: модель их не видит и не может вызвать.

| Инструмент | Что делает | Запрос к RX |
|---|---|---|
| `rx_complete_assignment` | выполнить задание с результатом | `POST Docflow/CompleteAssignment` |
| `rx_create_simple_task` | создать простую задачу исполнителям и стартовать | `POST Docflow/CreateSimpleTask`, затем `Docflow/StartTask` |
| `rx_abort_task` | прекратить задачу | `POST Shell/AbortTask` |

Перед каждым действием записи сервер запрашивает у хоста подтверждение пользователя (elicitation). Если хост elicitation не поддерживает, действие всё равно выполняется: флаг записи уже явное согласие, а хосты и сами спрашивают перед вызовом инструментов без `readOnlyHint`.

### Ресурсы

`rx://assignment/{id}`, `rx://task/{id}`, `rx://document/{id}`: те же карточки текстом, для подкладывания в контекст руками.

### Промпты

- `daily_review`: разбор моих заданий на сегодня, просрочки, порядок.
- `summarize_document`: краткое содержание документа по Id.

## Принципы

1. **Мало инструментов, крупных.** Не зеркалим OData: девять инструментов чтения покрывают рабочий день, а не тысячу сущностей.
2. **Текст, а не JSON.** Ответы форматируются компактным русским текстом: одна строка на задание, даты по-человечески, Id в скобках. Сырой OData модели не показываем.
3. **Лимиты везде.** Списки по умолчанию 20, максимум 100. Текст документа по умолчанию 20 000 символов. Тело документа не грузим, пока не попросят явно.
4. **Чтение по умолчанию.** Запись только по флагу и с подтверждением. Удаления нет вообще.
5. **Содержимое RX не доверенное.** Тема задания или текст документа могут содержать инструкции для модели. Сервер помечает такие данные как содержимое, а не команды, и никогда не выполняет цепочку «прочитал и сразу отправил» без явного вызова инструмента записи.
6. **Ничего не храним.** Нет кэша, нет базы, нет телеметрии. Пароль живёт в переменной окружения процесса, в логи не попадает.
7. **Совместимость.** Только стандартные сущности и действия платформы Sungero (Workflow, Docflow, Content, CoreEntities, Company, Shell). Прикладные модули заказчика не трогаем: они у всех разные.

## Модель ошибок

- 401/403 от RX: «нет прав или неверная учётка», без подробностей.
- 404: «объект не найден или недоступен» (RX не различает).
- Сетевые ошибки: адрес и таймаут, без тела.
- Ошибки инструментов возвращаются как `isError` с текстом для модели, чтобы она могла объяснить пользователю и не повторять вызов вслепую.

## Проверка на живой системе

`rxmcp check` делает только GET-запросы: метаданные, кто я, счётчик заданий, один документ, одна версия. Печатает, что работает, а что нет, и подсказывает, что поправить. Годится для рабочей системы.

## Структура кода

```
main.go                 команды: serve (по умолчанию), check, install, version
internal/config         переменные окружения и флаги
internal/odata          HTTP-клиент OData: GET/POST, аутентификация, ошибки, лимиты
internal/rx             доменные запросы и форматирование: задания, задачи, документы, люди
internal/textx          извлечение текста из docx/xlsx/txt/…
internal/server         регистрация инструментов, ресурсов, промптов в MCP
```
